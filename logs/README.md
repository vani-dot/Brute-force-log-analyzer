# Sample log files

**These are synthetic. None of it is real.**

Every file here was written by [`make_logs.py`](../make_logs.py) and
[`generate_log.py`](../generate_log.py), shaped from published descriptions of
how SSH brute force attacks look. Nothing was captured from a real host, and
there are no real addresses in any of it.

All addresses come from ranges reserved precisely so they can appear in
documentation without pointing at anybody:

| Range | Reserved by | Used here for |
|---|---|---|
| `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` | RFC 5737 | Attackers |
| `198.18.0.0/15` | RFC 2544 | Diffuse background scanning |
| `10.0.0.0/8` | RFC 1918 | The fictional office's own machines |

If you are demonstrating this tool and somebody asks where the logs came from:
they are demo data generated by the project itself, and the tool works exactly
the same on a real `/var/log/auth.log` you upload.

To rebuild them: `python make_logs.py`

## What each file does

Measured at the recommended setting, **4 failures within 600 seconds**:

| File | Lines | Events | Skipped | Findings | High |
|---|---:|---:|---:|---:|---:|
| `01-classic-burst.log` | 26 | 26 | 0 | 2 | 0 |
| `02-successful-breach.log` | 17 | 14 | 3 | 2 | 1 |
| `03-low-and-slow.log` | 96 | 96 | 0 | 0 | 0 |
| `04-botnet-subnet.log` | 54 | 54 | 0 | 2 | 0 |
| `05-password-spray.log` | 14 | 14 | 0 | 1 | 0 |
| `06-rsyslog-collapsed.log` | 4 | 61 | 2 | 2 | 0 |
| `07-everything.log` | 1114 | 708 | 441 | 8 | 1 |
| `background-noise.log` | 180 | 144 | 36 | 0 | 0 |
| `quiet-night.log` | 9 | 3 | 6 | 0 | 0 |
| `busy-office.log` | 144 | 80 | 64 | 2 | 0 |

### `clean/` — must find nothing

| File | Why it is here |
|---|---|
| `quiet-night.log` | Six hours of routine automation. The simplest negative case. |
| `background-noise.log` | One or two probes from ~90 addresses in as many networks. This is what an internet-facing host sees all day, and none of it is an attack. |

`background-noise.log` produces **zero** findings at 5/120 and 4/600 — and
**five** at 3/1800. That is not a bug in the file; it is the evidence for why a
threshold of 3 is too low. Ordinary scanning accumulates past three.

### `tricky/` — clean traffic that a naive setup flags anyway

| File | Why it is here |
|---|---|
| `busy-office.log` | A working day of real logins, many preceded by a mistyped password. Individually harmless. But every member of staff is on the same `/24`, so their typos aggregate into one subnet finding. |

The detector is behaving exactly as designed here and is still wrong, because
it has no way to know that `10.0.0.0/8` is yours. Put it in the allowlist —
`Never alert on` on the Analyse tab, or `BFLA_ALLOWLIST` — and the subnet
finding is suppressed and reported as suppressed rather than silently dropped.

This file is also why the compromise check has a second, higher bar. A user
mistyping their own password four times and then logging in used to be
reported as a confirmed breach. Failures against *several* accounts followed
by a success still fire at two attempts; failures against *your own* account
need to pass a much higher bar first.

### `attacks/` — one technique each

| File | Technique | Smallest setting that catches it |
|---|---|---|
| `01-classic-burst.log` | One address hammering `root`. The control case. | `3 / 120s` |
| `02-successful-breach.log` | Enumeration across four usernames that **succeeds**, then sudo to root. | `3 / 120s` |
| `03-low-and-slow.log` | One guess every ~7 minutes for 12 hours. | `3 / 1800s` |
| `04-botnet-subnet.log` | 18 addresses in one /24, 3 attempts each. | `3 / 120s` |
| `05-password-spray.log` | One password against 14 accounts from one source. | `3 / 120s` |
| `06-rsyslog-collapsed.log` | A 60-attempt flood folded by rsyslog into one line. | `3 / 120s` |
| `07-everything.log` | All of the above buried in a realistic 24h log. | `3 / 120s` |

Two of these are worth dwelling on.

**`03-low-and-slow.log` needs a 1800-second window.** At the recommended
4/600 it produces nothing at all. That is the honest limitation of a sliding
window: an attacker who spaces attempts wider than your window is invisible to
it. Only the compromise check would catch them, and only if they eventually
succeed.

**`02-successful-breach.log` is the one that matters.** Twelve failures is
below many burst thresholds, so a tool that only counts failures reports
nothing — while the log plainly shows the attacker logging in and running
`sudo bash`. Counting attempts and detecting breaches are different jobs.

## Using your own log instead

The samples exist so the tool can be demonstrated without waiting for someone
to attack you. For real use, feed it a real log:

```bash
# Linux
python main.py /var/log/auth.log          # Debian, Ubuntu
python main.py /var/log/secure            # RHEL, Fedora

# macOS has no plain-text sshd log, so export one first
log show --predicate 'process == "sshd"' --last 24h > ~/auth.log
python main.py ~/auth.log
```

Or drop the file onto the Analyse tab in the web app. Nothing is uploaded
anywhere — the analysis runs in the process you started.
